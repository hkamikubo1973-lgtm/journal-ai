# journal-ai 正式UI化 Phase 3 マスター選択UI設計前調査

調査基準コミット: `594794f`

対象: 通常仕訳のReact編集フォーム。今回は調査・設計のみとし、API、React、Streamlit、マスターCSVは変更しない。

注記: 調査時点で `data/` には既存の未コミット差分がある。以下の件数と重複状況は調査時の作業ツリーを読んだ結果であり、確定仕様ではない。

## 1. 調査目的

React版の科目・補助・部門を個別の自由入力からマスター選択へ移行する前に、現行Streamlit版の読み込み、初期値、選択肢、不一致時の挙動を明らかにする。あわせて、次を満たすReact/FastAPI設計を決める。

- コードと名称を一つの選択として扱い、組み合わせのずれを防ぐ。
- 過去仕訳にしか存在しない値を画面から消さず、安全に解決させる。
- 現行 `prepare-registration` のsnake_caseリクエストとの互換性を保つ。
- 「資金複合」「諸口」を通常1行仕訳の選択可能科目にしない。
- マスターCSVの現状以上の関係をAPIで捏造しない。
- 伝票日付をカレンダー入力にし、API境界で既存の `YYYYMMDD` に正規化する。

結論は次のとおり。

1. 初期版はまとめて取得する `GET /api/journal/masters` が適する。
2. APIは名称キーのdictではなく、コードを識別子とする行配列を返す。
3. 現在の件数では依存なしの標準 `<select>` が安全である。検索可能comboboxは別Phaseで要件とライブラリを評価する。
4. `editForm` の平坦なコード・名称フィールドは維持し、選択変更時に両方を原子的に更新する。名称は直接編集させない。
5. マスター不一致値は一時的な「現在値」として表示するが、警告し、利用者が有効なマスターを明示選択するまで登録準備を許可しない。
6. `sub_master.csv` には親科目コードがないため、現状では科目別絞り込みを正しく実装できない。スキーマ方針の確定が先に必要である。

## 2. 現行Streamlit版のマスター利用

### 読み込み

`src/app.py` は起動時に次のグローバル辞書を作る。

| マスター | 読み込み関数 | 保持形式 |
|---|---|---|
| 科目 | `load_account_master()` | `{name: code}` |
| 補助 | `load_sub_master()` | `{name: code}` |
| 部門 | `load_department_master()` | `{name: code}` |

各CSVは `utf-8-sig` で読む。画面用リストは辞書のキー、つまり名称をソートした配列である。科目・補助・部門の生成ボタンは過去仕訳の借貸両側から `(code, name)` を収集し、CSV全体を書き直す。

名称を辞書キーにする現行方式には次の制約がある。

- 同名でコードが異なる科目は後に読んだコードだけが残る。
- 補助コードは複数科目で再利用されるため、コード単体をグローバルIDにできない。
- コードと名称の両方を持つ元行でも、通常仕訳のselectは名称を値として扱う。

### 通常仕訳での利用箇所

- 検索条件の部門: `[''] + department_master` のselectbox。
- 伝票日付: 画面共通の `st.date_input()`。初期値は当日で、`strftime('%Y%m%d')` して編集行へ設定する。
- 借方・貸方科目: 名称のselectbox。推奨候補を先頭へ並べ、残りの科目を続ける。
- 借方・貸方補助: `[''] + sub_master` の全件selectbox。
- 通常仕訳の編集欄: 部門selectは存在しない。元のエプソン行にある借貸部門を変更せず保持する。
- 出力時: 科目名、補助名からコードを辞書で再解決し、解決できない場合は元行コードへフォールバックする箇所がある。

### マスター管理

Streamlitの通常仕訳サイドバーには科目候補の追加機能がある。コード、名称、分類を入力し、任意で入金科目候補にも追加する。重複コードと重複名称を検査するが、既存CSVには同名異コードが存在するため、生成データと手動追加規則は完全には一致していない。

調査した通常仕訳の管理導線には、既存行の個別編集・削除は見当たらない。生成ボタンによる全体再作成と、新規候補の追記が中心である。

React版のマスター選択とマスター編集は責務を分ける。初期版APIは読み取り専用とし、追加・修正UIは別Phaseにする。

## 3. account_master.csv の構造と科目選択

### 構造

列は次の3つである。

| 列 | 意味 | API型 |
|---|---|---|
| `code` | 科目コード | string |
| `name` | 科目名 | string |
| `category` | 分類 | string |

調査時点では101行、コード重複0、名称重複9組、空コード・空名称0で、`category` は全行空だった。同名異コードの例として「法定福利費」「福利厚生費」「燃料費」などがある。このため、名称を一意キーとして扱ってはならない。

### Streamlit版の選択

通常仕訳では `build_account_select_options()` が次の順に名称リストを作る。

1. 検索文脈、相手科目、補助から得た推奨科目
2. 同一伝票ブロックから推定した置換候補
3. その他の科目マスター
4. 現在値がマスター外なら、除外科目でない限り先頭へ追加

表示値は原則科目名であり、推奨候補には「推奨」等のラベルを付ける。コードは選択時ではなく、出力時に名称から解決する。

### 資金複合・諸口

`engine.EXCLUDED_SUGGESTION_ACCOUNTS` は「資金複合」「諸口」を定義し、通常仕訳の科目選択肢から除外する。元候補が該当する場合は先頭選択へせず、利用者へ実科目への変更を促す。調査時点のマスターには「資金複合」コード1241、「諸口」コード999が存在する。

React版APIでは、これらをレスポンスから削除せず `selectable: false` として返すことを推奨する。理由は、過去値の照合と警告表示には存在情報が必要だからである。通常の選択肢には出さず、過去値として来た場合だけ「選択不可・要変更」と表示する。

### React表示と内部値

表示はコードと名称を併記する。

```text
203　1年内返済長期借入金
114　普通預金
```

選択の識別子は `code` とし、選択した行から `code` と `name` を同時にフォームへ反映する。同名異コードを区別できるよう、labelだけでなくoptionのvalueもコードにする。

## 4. sub_master.csv の構造と補助選択

### 構造と重大な制約

列は `code,name` の2つだけで、親科目コード列はない。調査時点では18行、名称重複0、コード重複4グループである。コード1、2、3、6などが異なる補助名で繰り返し使われている。

したがって、現状のCSVから次は判定できない。

- 補助がどの科目に属するか。
- 同じ補助コードのどの名称が、選択中の科目に対して正しいか。
- 科目変更後に現在の補助を維持できるか。

### Streamlit版の選択

`build_sub_options(current_sub)` は常に空欄と全補助名を返す。科目選択後の絞り込みは行っていない。借方・貸方で同じ全件リストを使う。

過去行の補助名がマスターにない場合は、その現在値を一時的に選択肢末尾へ追加する。この点は「過去値を消さない」という意味でReact版にも引き継ぐ価値があるが、現行は警告や登録ブロックを行わない。

### 推奨方針

補助なしは空文字 `code: '', name: ''` として明示する。初期版はデータが表現できる範囲を超えず、全補助から選ぶ標準selectとする。ただしlabelは必ず `code　name` とし、同じコードの別補助を区別する。親科目のない現行データでは補助コードだけが一意でないため、optionの内部valueにはコード単体を使わず、コードと名称の複合値または配列上の安定キーを使い、選択後に元の行から両方を取得する。

科目別絞り込みを実装する前に、次のいずれかを決める必要がある。

1. `sub_master.csv` に `account_code` を追加して複合キー `(account_code, code)` を正式IDにする。
2. 新しい関係マスターを別ファイルで管理する。
3. 過去仕訳から関係を推定してAPIで返す。ただし未出現の正規組み合わせを失い、誤った過去データも正として扱うため、補助的用途に限定する。

安全性から1または2を推奨する。仕様確定前にAPIが架空の `account_code` を付与してはならない。

## 5. department_master.csv の構造と部門選択

### 構造

列は `code,name`。調査時点では4行で、コード・名称の重複と空値はない。

### Streamlit版の扱い

検索条件では空欄を含む部門名selectを使い、検索エンジンへ部門名を渡す。一方、通常仕訳の候補編集フォームには借方・貸方の部門selectがなく、元行の `借方部門/借方部門名` と `貸方部門/貸方部門名` を保持する。

したがって「検索条件の部門」と「仕訳行の部門」は別の状態である。検索条件を編集行へ自動転記してはならない。

### React版の推奨

- 検索条件の部門: 従来どおり1つ。候補の絞り込みだけに使用する。
- 編集フォームの部門: 借方・貸方に別々の選択を持つ。
- 部門なし: 空文字の選択を許可する。
- 表示: `10　タクシー事業` のようにコード＋名称とする。
- 候補初期値: 各側の元コード・元名称から独立して照合する。

過去データと未収消込処理には貸方部門を設定するコードがあるため、貸方部門を常に空と仮定してはならない。

なお、React版での借貸部門編集は現行Streamlit通常仕訳より広い機能である。`prepare-registration` は現在これらをプレビューへ反映するため、正式仕様として採用するか、Streamlit互換で元値固定にするかを実装前に決める必要がある。

## 6. payment_accounts.csv の位置づけ

列は日本語の `科目` 1列で、科目名だけを持つ。調査時点では4件である。

用途は未収消込の入金科目selectである。通常仕訳の借方・貸方selectは `account_master.csv` を使い、`payment_accounts.csv` では絞らない。通常仕訳サイドバーから科目を追加する際、任意で入金科目候補にも登録できるだけである。

また、調査時点では4件のうち「電子記録債権」が科目マスターに存在しない。名称だけのリストなので、通常仕訳のコード・名称ペアを保証するマスターとして利用できない。

結論として、`GET /api/journal/masters` には含めない。未収消込をReact化する際に、例えば `GET /api/receivables/masters/payment-accounts` として別APIにし、科目マスターとの不一致もレスポンスまたは警告で示す。

## 7. 候補DTOから編集フォームへの初期値反映

### 現行Streamlit

候補行は元のエプソン列を持つ。科目selectの初期値は `借方科目名/貸方科目名` が名称リストにあるかで決め、なければ通常は先頭を選ぶ。ただし候補編集時の科目選択肢生成では、除外科目でなければ現在値を追加する。

補助は元の補助名を使い、マスター外なら一時選択肢へ追加する。部門は編集しない。日付は候補日付ではなく画面共通の日付input（初期値は当日）で上書きする。

### 現行React DTO

`journal_search_service.serialize_source_rows()` と `build_editable_rows()` は元行の日本語列を維持する。Reactの `buildEditFormFromRow()` は次をそのままコード・名称フィールドへ写す。

- `借方科目` / `借方科目名`
- `借方補助` / `借方補助科目名`
- `借方部門` / `借方部門名`
- 貸方側の同等列
- `伝票日付`

名称からコードを引き直してはいない。これは移行時の初期値として正しい。マスター取得後の照合順序は次を推奨する。

1. コード・名称が同じマスター行に完全一致: その行を選択する。
2. コードだけ一致し名称が違う: 元ペアを一時表示し警告。自動で名称を書き換えない。
3. 名称だけ一致しコードが違う、または同名候補が複数: 元ペアを一時表示し警告。推測選択しない。
4. どちらも不一致: 「マスター外の現在値」として表示し警告。
5. 資金複合・諸口: 選択不可の現在値として表示し、実科目選択を必須にする。

不一致時に元値を消したりselect先頭へ黙って置換すると誤登録になる。選択状態とは別に `resolved | legacy | mismatch | excluded` の解決状態をReactで持つと表示と登録可否を整理しやすい。

## 8. React版マスター取得API案

### 推奨: まとめて取得

初期版は次を推奨する。

```text
GET /api/journal/masters
```

理由:

- 編集開始時に科目・補助・部門の全てが必要で、1回の取得でよい。
- 同一スナップショットとして照合できる。
- 現在の規模（約100科目、数十補助、数部門）は小さい。
- loading/error/retry状態が一組で済む。
- HTTP呼び出しとPydantic型が増えない。

想定レスポンス:

```json
{
  "accounts": [
    {
      "code": "203",
      "name": "1年内返済長期借入金",
      "category": "",
      "label": "203　1年内返済長期借入金",
      "selectable": true,
      "unselectable_reason": null
    },
    {
      "code": "999",
      "name": "諸口",
      "category": "",
      "label": "999　諸口",
      "selectable": false,
      "unselectable_reason": "complex_account"
    }
  ],
  "sub_accounts": [
    {
      "account_code": null,
      "code": "8",
      "name": "埼玉りそな駅前",
      "label": "8　埼玉りそな駅前",
      "scope": "global"
    }
  ],
  "departments": [
    {
      "code": "10",
      "name": "タクシー事業",
      "label": "10　タクシー事業"
    }
  ],
  "meta": {
    "sub_account_relation_available": false
  }
}
```

`account_code: null` と `scope: global` は現行補助マスターの制約を明示するための移行表現である。親関係が正式化した後に `account_code` を必須にする。

### 分割APIとの比較

```text
GET /api/journal/masters/accounts
GET /api/journal/masters/sub-accounts
GET /api/journal/masters/departments
```

分割方式は、マスターごとのキャッシュ、権限、巨大データの遅延取得には向く。一方、初期版ではリクエスト、エラー状態、型、テストが増える。将来補助を `?account_code=114` でサーバー絞り込みする規模になった時点で分割または専用endpointを追加すればよい。

### サーバー実装上の注意

- `app.py` をimportせず、FastAPI非依存の読み取りサービスを新設する。
- CSV行をlistのまま保持し、名称dictへ潰さない。
- 全値を文字列としてtrimする。
- 空コード・空名称、重複コード、同名異コードを診断できるようにする。
- 「資金複合」「諸口」のselectable判定は既存定数と一元化する。
- 読み取り専用とし、API呼び出しでCSVを書き換えない。

## 9. React版select / combobox設計案

| 案 | 長所 | 短所 | 評価 |
|---|---|---|---|
| A. 標準 `<select>` | 依存なし、アクセシビリティとキーボード操作がブラウザ標準、値の制約が容易 | 部分一致検索が弱い、件数増加時に探しにくい | 初期版に推奨 |
| B. `<datalist>` | 依存なし、文字入力で候補を絞れる | 任意文字を確定できる、コード・名称ペアを強制しにくい、表示差が大きい | 非推奨 |
| C. 自作combobox | 要件に合わせられる | ARIA、フォーカス、IME、矢印キー、外側クリック等が複雑 | 初期版では非推奨 |
| D. ライブラリ | 検索、キーボード、仮想化を得やすい | 依存、CSS、更新、バンドル、選定コスト | 件数増加後に評価 |

調査時点の規模なら、まず標準selectで `code　name` を表示する。科目約100件で実務上不足が確認された場合は、独自実装へ直行せず、アクセシブルなcomboboxライブラリを比較する。補助の親関係が未確定な状態で検索UIだけ高度化しても誤選択リスクは解消しない。

科目名・補助名・部門名の自由入力欄は廃止し、選択された名称をread-onlyテキストまたはselect labelとして表示する。

## 10. コード・名称連動方針

### editFormは当面維持

既存の `JournalEditForm` はコード・名称を平坦に持ち、`prepare-registration` も同じ組み合わせをsnake_caseで受ける。初期移行では型をネストへ変更せず、次のフィールドを維持する。

```ts
debitAccountCode
debitAccountName
debitSubCode
debitSubName
debitDeptCode
debitDeptName
// credit側も同様
```

selectのchange handlerは選択されたマスター行を受け、コードと名称を一度の `setEditForm` で同時更新する。名称だけの直接編集は禁止する。

この方式の利点:

- 現行prepare APIを変更しない。
- 既存の変更表示、リセット、カート表示を維持できる。
- API送信時に名称を再検索する必要がない。
- マスター外の過去値を一時保持できる。

将来フォーム全体を再設計する場合は `MasterSelection` へのネストを検討できるが、select化と同時に行う必要はない。

### サーバー検証

Reactで連動してもクライアント値は信頼しない。`prepare-registration` の将来Phaseでは、サーバーがコードを主キーとして名称を照合する。

- 完全一致: 受理。
- コードあり・名称違い: エラーにし、黙って補正しない。
- コードなし、選択不可科目、曖昧な同名: エラー。
- 補助なし: コード・名称が両方空なら受理。
- 部門なし: コード・名称が両方空なら受理。

## 11. マスター不一致時の扱い

初期版は「A. 警告して表示」「C. 一時候補」「B. 登録境界でブロック」を組み合わせる。

1. 候補DTOの元コード・名称を一時optionとして表示する。
2. 「現在のマスターに存在しません」または「コードと名称が一致しません」と警告する。
3. 利用者が有効なマスター行を選び直すまで、登録予定への追加を無効化するかprepareでblockedにする。
4. 元値を自動で先頭の有効科目へ置き換えない。
5. マスター追加は別Phaseの管理導線とし、通常仕訳の編集中にCSVへ直接追加しない。

これにより、過去値の可視性を保ちながら誤登録を防ぐ。名称だけ一致した場合も、同名異コードが実在するため自動解決しない。

## 12. 日付input改善方針

Reactは `<input type="date">` を採用する。

- 画面状態と表示: `YYYY-MM-DD`
- 候補DTO: `YYYYMMDD` を `YYYY-MM-DD` へ変換して初期表示
- API送信: `YYYY-MM-DD` のまま送ってもよい。現行prepareサービスは両形式を受け、`YYYYMMDD` へ正規化する。
- APIレスポンスとエプソンプレビュー: `YYYYMMDD`
- 不正な候補日付: 空欄＋警告。推測変換しない。

主入力で8桁自由入力を併用するとブラウザ検証を弱め、状態形式が二重になるため、初期版では許可しない。既存利用者に8桁貼り付け需要がある場合は、別の貼り付け変換導線として要件化する。

Streamlit版は候補日付ではなく当日を初期値にする一方、現行Reactは候補日付を引き継ぐ。正式UIでどちらを採用するかは要確認だが、過去仕訳を雛形として使う通常運用では、誤って過去年を登録しないよう当日初期値も合理的である。候補日付を表示する場合は過去日警告が必要である。

## 13. 実装Phase案

### Phase 3-4: マスター読み取りサービスとAPI

- FastAPI非依存のマスター読み取りサービスを追加する。
- `GET /api/journal/masters` とPydanticレスポンスを実装する。
- 同名異コードを失わない配列、`selectable`、補助関係未対応metaを返す。
- 正常、空行、重複、資金複合・諸口、ファイル読込失敗をテストする。
- 副作用がないことを検証する。

### Phase 3-5: Reactでマスター取得・保持

- 初回取得、loading、error、retryを実装する。
- 候補DTOとマスターの照合結果を作る。
- このPhaseでは既存inputを残し、診断JSONまたは警告表示までに限定できる。

### Phase 3-6: 科目select化

- 借方・貸方をコード値の標準selectへ変更する。
- コード・名称を原子的に更新する。
- 資金複合・諸口とマスター不一致を選択不可・要変更にする。
- 同名異コードの表示とリセットをテストする。

### Phase 3-7: 補助関係仕様確定と補助select化

- 先に親科目との関係をどこに保持するか決める。
- 関係未導入なら全件selectであることを明示する。
- 関係導入後は科目変更時に補助候補を絞り、現在補助が不適合なら空へ黙って変更せず警告する。
- 借方・貸方、補助なし、同一コード再利用をテストする。

### Phase 3-8: 部門select化

- 検索条件と編集行の部門stateを分離する。
- 借方・貸方それぞれに空欄可能なselectを実装する。
- 元雛形保持との仕様差を確定し、プレビュー反映をテストする。

### Phase 3-9: 日付inputのdate化

- DTO→表示、表示→APIの変換helperを追加する。
- 正常日、閏日、不正日、空欄、過去日・未来日表示をテストする。

### Phase 3-10: prepare-registrationのマスター整合検証

- サーバーで科目・補助・部門のコード名称ペアを再検証する。
- legacy/mismatch/excludedを構造化エラーで返す。
- React側の選択済み値だけでなく、直接APIを呼ぶ不正値も拒否する。
- CSV保存・DB登録は引き続き行わない。

補助の親関係が早期に決まらない場合、Phase 3-7を保留して部門・日付を先行してよい。ただしPhase 3-10で補助の完全な親科目検証ができないことを明示する。
