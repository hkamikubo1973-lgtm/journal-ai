# journal-ai 正式UI化 Phase 3 補助科目設計調査

## 1. 調査目的

Phase 3-6でReact編集フォームの借方・貸方科目はマスター選択になり、科目コードと名称を一組で更新できるようになった。一方、補助コードと補助名は引き続き別々の自由入力であり、現行 `sub_master.csv` には親科目コードがない。

本調査の目的は、補助をselect化する前に次を明らかにすることである。

- 現行補助マスターの一意性と欠落情報
- Streamlit版が補助の初期値、選択肢、科目変更をどう扱うか
- 過去仕訳から親科目関係をどの程度推定できるか
- 正式な親子関係マスターの候補と移行上の影響
- Reactと `prepare-registration` が補助を安全に扱うための段階的な方針

今回は調査と設計のみとし、`src/`、`frontend/`、`data/`、`config/` および既存設計書は変更しない。集計値は調査時点の作業ツリーにあるCSVを読み取り専用で確認した結果である。

### 結論

1. 補助コードはグローバルには一意でなく、正式な識別単位は少なくとも `(account_code, sub_code)` とする必要がある。
2. `transactions.csv` から現行18補助すべての親候補を一意に抽出できるが、過去実績は正規マスターではなく移行時の候補データとしてのみ使う。
3. 目標形は `sub_master.csv` に `account_code` を追加する案Aを推奨する。1行が一つの有効な親子関係を表し、React/API/CSV間の正本を一つにできるためである。
4. 親関係が正式化されるまではReactの補助自由入力を維持する。科目変更時だけは、古い補助を黙って残さずコード・名称を一組でクリアして警告する。
5. 補助selectを公開する前に、マスターAPIの親情報対応と `prepare-registration` のサーバー側整合検証をそろえる。

## 2. sub_master.csv の現状

### 構造と件数

`data/sub_master.csv` の列は次の2列だけである。

```csv
code,name
```

調査結果は次のとおりである。

| 確認項目 | 結果 |
| --- | ---: |
| 行数 | 18 |
| 空コード | 0 |
| 空名称 | 0 |
| 同名・異コード | 0 |
| 同一コード・同一名称の重複行 | 0 |
| 複数名称を持つコード | 4コード |
| `account_code` 列 | なし |

名称は現在のデータでは一意だが、これはスキーマ上の保証ではない。`src/app.py` の `load_sub_master()` は `{name: code}` の辞書へ読み込むため、将来同名補助が追加されると後勝ちで上書きされる。また、`journal_master_service.py` は配列としてコード・名称を保持するものの、親科目は返せない旨を常に警告している。

### 現行生成処理の制約

Streamlitの「補助マスター生成」は過去仕訳の借貸両側から `(sub_code, sub_name)` を収集し、`sub_master.csv` 全体を `code,name` の2列で書き直す。親科目を収集していないため、単にCSVへ列を手作業で追加しても、現行生成ボタンを実行すると親情報が失われる。

案Aを採用する場合、Phase 3-11で少なくとも次を同時に変更する必要がある。

- 生成キーを `(account_code, sub_code, sub_name)` にする
- 出力列を `account_code,code,name` にする
- 読み込み側を名称キー辞書から親科目を含む行配列または複合キー辞書へ移す
- 既存Streamlitの全件補助selectを移行期間中も動かす互換処理を用意する
- 生成ボタンが正式マスターを無条件上書きしてよいかを再検討する

## 3. Streamlit版の補助科目処理

### 通常仕訳編集での選択

`src/app.py` の通常仕訳編集画面と確認済み仕訳の再編集画面では、借方・貸方補助はいずれも `st.selectbox` である。選択肢は `build_sub_options(current_sub)` が作り、常に次の構成になる。

```text
空欄 + sub_master.csv の全補助名（名称順）
```

科目別の絞り込み、借貸別の違い、親科目照合はない。元仕訳の補助名がマスターに存在しない場合は、その名称を一時的に末尾へ追加するため、過去値は表示上失われない。ただし、その値がマスター外であるという警告も登録ブロックもない。

### 初期値とコード・名称連動

- 初期表示は元行の `借方補助科目名` / `貸方補助科目名` を使う。
- 編集中に保持するのも補助名であり、補助コードを同時更新しない。
- 通常仕訳の出力行を組み立てる段階で、補助名を `SUB_MASTER` の `{name: code}` から逆引きする。
- 解決できない場合に元行の補助コードへフォールバックする経路があり、編集後の名称と古いコードが組み合わさる余地がある。

### 科目変更時

科目selectと補助selectは独立している。科目を変更しても補助の選択肢は同じ全件であり、widget state上の補助はそのまま残る。警告も自動クリアもない。そのため、例えば `114 普通預金 + 1 埼玉りそな東松山` の補助を残したまま親科目だけを `208 預り金` に変えることができる。

### 補助なし・マスター外・除外科目

- 補助なしは空文字のoptionで表す。
- マスター外の元補助名は一時optionとして保持される。
- `資金複合` / `諸口` は科目として別ロジックで選択対象外になるが、補助側に追加制御はない。
- 現行Streamlitには `(account_code, sub_code, sub_name)` を原子的に検証する処理がない。

過去値を勝手に消さない点は参照画面として有用だが、編集可能な登録経路では不整合を通す。Reactへは「元値を可視化する」考え方だけを引き継ぎ、「不適合なまま登録準備できる」挙動は引き継がない。

### 推定精度の評価

現在のデータに対する整合率は高い。18組すべてが一意で、コード・名称の片側欠落や同一親内の矛盾もないため、案Aの初期CSVを作る材料としては十分である。

- `sub_master.csv` 自体が過去仕訳から生成されるため、両者の完全一致は独立した正当性の証明ではない。
- 過去に一度も使われていない正規の補助は抽出できない。
- 誤入力された過去仕訳を正しい関係として取り込む可能性がある。
- 1件だけの関係が3組あり、頻度による信頼度は低い。

したがって、履歴集計は「移行候補CSVの生成 → 管理者レビュー → 正式マスターとして確定」の順で利用する。実行時に毎回履歴から親関係を推定する案Cは採用しない。

## 5. 補助マスター拡張案

### 比較

| 案 | 安全性 | 既存影響 | 運用性 | 評価 |
| --- | --- | --- | --- | --- |
| A. `sub_master.csv` に `account_code` を追加 | 親子関係とコード・名称を1行で原子的に管理できる | 生成処理、読込処理、Streamlit互換の変更が必要 | 正本が一つで分かりやすい | **目標形として推奨** |
| B. `sub_account_relations.csv` を新設 | 既存CSVを壊さず段階移行できる | APIで2ファイルjoin、欠落・重複検証が必要 | 名称を両方へ持つと不整合、持たないと複合ID設計が必要 | 移行事情が強い場合の代替 |
| C. `transactions.csv` から都度推定 | CSVスキーマ変更なし | 実行時集計、曖昧時処理、履歴保持範囲への依存が増える | 未使用の正規関係を表せず誤履歴も採用する | 移行候補生成に限定 |
| D. 初期版は自由入力維持＋警告のみ | 現行値を失わず小さく進められる | 誤入力リスクとAPIの検証不能が残る | 短期の暫定策として容易 | Phase 3-11までの暫定策 |

### 案Aの推奨スキーマ

```csv
account_code,code,name
114,8,埼玉りそな駅前
114,1,埼玉りそな東松山
208,1,社会保険料
```

設計ルールは次とする。

- 一意キーは `(account_code, code)` とする。
- 同じ `code` を別の `account_code` で再利用できる。
- 同一親科目内で一つのコードに複数名称を許可しない。
- 同じ名称を複数親科目で使う可能性は排除せず、名称をIDにしない。
- API/UIの選択値は単独コードではなく、選択中の親科目を文脈にした複合キーで解決する。
- 表示labelは `code　name` とし、選択時にコードと名称を同時更新する。
- 補助なしはCSV行を作らず、フォーム上の `code: '', name: ''` で表す。

現在のStreamlit readerは追加列を無視するため、列追加だけなら即時に例外にはならない。しかし生成処理が列を消すこと、名称辞書が将来の同名補助を上書きすることから、CSVだけを先行変更してはならない。Phase 3-11でデータ移行、reader、generator、API、互換確認を一つの変更単位にする。

### 案Bを選ぶ条件

既存 `sub_master.csv` を外部システムが固定2列で参照しており変更できない場合に限り、次の関係ファイルを暫定採用する。

```csv
account_code,sub_code,sub_name
114,8,埼玉りそな駅前
```

この場合も `(account_code, sub_code)` の一意制約、`(sub_code, sub_name)` が既存 `sub_master.csv` に存在すること、孤立行と不足行の診断が必要である。2ファイルのどちらが名称の正本かを決めなければならないため、長期の最終形にはしない。

## 6. React版での初期推奨方針

### 親関係導入前

Phase 3-11で正式マスターを導入するまでは、補助コード・補助名の自由入力を維持する。全件selectへ急いで変えると、同じコードの別名称を選択中科目と無関係に選べるため、見た目だけ安全なUIになる。

暫定期間にも次を行う。

- コードだけ、名称だけの入力をエラー表示する。
- `sub_master.csv` に存在しない `(sub_code, sub_name)` はエラー表示する。
- グローバルに組が存在しても親関係は未検証である旨を警告する。
- 元候補の値は初期表示で保持し、マスター外値なら明示的に「要修正」とする。
- `prepare-registration` の前にコード・名称をtrimし、一組として扱う。

### 親関係導入後

借方・貸方それぞれの補助を、選択中科目に属する補助だけを返す標準selectへ変更する。

- 先頭optionは「補助なし」とする。
- option labelは `code　name`、選択値はその親科目内の補助コードとする。
- 選択イベントで補助コードと補助名を原子的に更新する。
- マスター取得中・取得失敗時はselectを無効化する。
- 初期値が現行マスターと一致しない場合、値を黙って捨てず、フォーム上部に元値を表示して「補助なし」または有効値の選び直しを要求する。
- 借方と貸方は同じcomponentを利用し、必ず各側の科目コードをfilter条件にする。

### 登録可能条件

Reactの表示上の警告だけに依存せず、最終的にはAPIの検証結果が成功した場合だけ登録予定カートへ追加する。マスター取得不能、部分入力、コード・名称不一致、親科目不一致は登録準備を止める。

## 7. 科目変更時の補助扱い

### 推奨動作

借方または貸方科目が実際に別コードへ変更されたとき、同じ側の補助を次の順で扱う。

1. 補助コード・名称がともに空なら何もしない。
2. 親関係マスター導入後で、現在の `(sub_code, sub_name)` が変更後科目でも完全一致するなら保持する。
3. それ以外は補助コードと補助名を同時に空へクリアする。
4. 「科目を変更したため、以前の補助をクリアしました。必要なら選び直してください」と警告する。

現行18関係では同一のコード・名称組が複数親に属する例はないため、実データ上は科目変更時にほぼ必ずクリアされる。

### 自動クリアを推奨する理由

古い補助を残して警告だけにすると、警告の見落としや直接API呼び出しにより不整合が残る。反対に、黙ってクリアすると利用者が変更に気付かない。コード・名称を原子的にクリアし、警告と変更表示を残す組み合わせが安全である。

候補を選び直す、または「候補選択時の値に戻す」を実行した場合は、科目と補助を含むフォーム全体を初期値へ戻す。React state更新では科目と補助を一回の更新で変更し、一瞬だけ古い補助が新しい科目に紐づく状態を作らない。

### 親関係導入前の暫定動作

正しい保持可否を判定できないため、科目コードが変わり、補助が入力済みなら常にコード・名称をクリアして警告する。利用者が同じ補助を必要と判断した場合だけ再入力させる。これは親関係を推測して保持するより保守的である。

## 8. prepare-registration での補助検証方針

### 現状

現行 `prepare_registration()` は、日付、金額、借方・貸方科目コードの必須性、通常1行仕訳であることを検証する。補助コード・補助名はtrimしてプレビューへそのまま転記し、次を検証していない。

- 補助コードと名称の片側欠落
- `sub_master.csv` におけるコード・名称一致
- 選択中科目との親子関係

React側にはグローバルな存在確認があるが、コード重複時は警告に留まり、親関係は確認できない。直接APIを呼べばクライアント検証も通らない。

### 親関係導入前の段階的検証

正式な親情報がない間にAPIが履歴から親を推測してブロックしてはならない。導入前にサーバー検証を追加する場合は次の範囲に留める。

| 状態 | 判定 |
| --- | --- |
| コード・名称が両方空 | 正常（補助なし） |
| 片方だけ入力 | blocked / error |
| `(sub_code, sub_name)` が現行マスターにない | blocked / error |
| 組は存在するが親関係を確認できない | warning |

コードは存在するが名称が一致しない場合は、自動で名称を補正せずerrorにする。コードがグローバルに重複するため、サーバーが名称を推測すると別補助へ置換する危険がある。

### 親関係導入後の厳格検証

借方・貸方を独立に、次の順で検証する。

1. 科目コード・科目名が科目マスターで完全一致し、選択可能であること。
2. 補助コード・名称が両方空、または両方入力であること。
3. 入力ありなら `(account_code, sub_code)` が補助マスターに存在すること。
4. その行の `name` が入力された補助名と完全一致すること。
5. 一致しない場合は登録予定行を作らずblockedにする。

| 不整合 | 推奨判定 |
| --- | --- |
| 補助コードがどの親にも存在しない | error |
| 補助コードは別科目にだけ存在する | error（親科目不一致） |
| 同一親・コードだが名称不一致 | error |
| 補助名は同一親にあるがコード不一致 | error |
| マスター行が重複または同一キー複数名称 | server configuration error |
| マスター自体を読み込めない | service error。登録準備不可 |

名称の全角・半角や互換文字をNFKCで正規化する場合も、CSV読込値とリクエスト値へ同じ処理を適用する。表示用の正式名称はマスター値を返してよいが、不一致リクエストを黙って成功させてはならない。

### APIレスポンスとテスト観点

`blocked` と人間向け文字列だけでなく、将来は側と理由を識別できる構造化エラーを検討する。

```json
{
  "field": "debit_sub_code",
  "code": "sub_account_parent_mismatch",
  "message": "借方補助は選択中の借方科目では利用できません。"
}
```

最低限、補助なし、借方のみ、貸方のみ、同一コードの別科目利用、コード・名称不一致、科目変更直後、マスター取得失敗、直接API呼び出しをテストする。

## 9. 実装Phase案

安全性と依存関係から、次の順を推奨する。

### Phase 3-7: 補助親関係の設計調査

- 本調査で現行構造、履歴関係、移行案を確定する。
- 目標形を案A、履歴利用を移行候補生成に限定する方針について業務確認を得る。

### Phase 3-8: 科目変更時の補助ガード

- 親関係導入前は、科目変更時に入力済み補助のコード・名称を原子的にクリアする。
- 警告表示、変更表示、リセットを追加する。
- 補助自由入力自体は維持する。

### Phase 3-9: 日付inputのdate化

- 表示形式とAPI形式の変換、不正日、過去日・未来日を整理する。

### Phase 3-10: 部門select化

- 借貸部門の空欄option、コード・名称連動、API反映を実装する。

### Phase 3-11: 補助マスター拡張と移行

- `sub_master.csv` を `account_code,code,name` へ移行する。
- 履歴から作った18候補を管理者確認後に投入する。
- Streamlit reader/generator、マスターAPI、診断情報、型を親関係対応にする。
- 移行前後の互換性と、生成ボタンによる親情報消失をテストする。

### Phase 3-12: サーバー側補助検証

- `prepare-registration` で科目、補助、部門のコード・名称と親子関係を再検証する。
- 不整合を構造化errorとして返し、直接API呼び出しも拒否する。
- CSV保存やDB登録はまだ行わない。

### Phase 3-13: React補助select化と統合

- 選択科目で絞った補助selectを借貸両側へ導入する。
- コード・名称の原子的更新、補助なし、legacy値、マスター再取得を扱う。
- UI検証とAPI検証を結合テストする。

当初案のように補助selectをAPI再検証より先に実装すると、画面経由では安全に見えても直接APIで不正な組を作れる期間が生じる。Phase 3-12と3-13は同一リリースにまとめるか、少なくともサーバー検証を先に配置する。
